Git의 4가지 영역과 기본 명령어

Git의 거의 모든 명령은 Working Directory → Staging Area(Index) → Local Repository → Remote 네 영역 사이에서 스냅샷을 옮기는 일입니다. 어떤 명령이 어느 영역을 건드리는지 몸에 익혀 두면 "지금 내 변경은 어디에 있지?"라는 질문에 항상 답할 수 있습니다.

📁 Working Directory실제 파일. git status 에서 빨간색

🧺 Staging Area (Index)다음 커밋에 포함될 스냅샷. 초록색

📚 Local Repository.git/ 안의 커밋 객체들 (DAG)

☁️ Remote (origin)GitHub/GitLab. 팀의 공통 기준

🔧 자주 쓰는 기본 명령

git init현재 폴더를 저장소로 초기화 (.git 생성)
git status영역별 변경 상태 확인. 막히면 무조건 이것부터
git add -p변경 덩어리(hunk) 단위로 골라서 스테이징
git diff / --stagedWD↔Index / Index↔HEAD 차이
git commit -m "msg"스테이징된 스냅샷으로 커밋 객체 생성
git log --oneline --graph --all그래프 형태로 이력 보기 (alias 추천)
git restore <f> / --stagedWD 변경 되돌리기 / 스테이징 취소
git stash / stash pop작업 중 변경을 임시 보관 / 복원

🧠 멘탈 모델: 커밋은 "차이"가 아니라 "스냅샷"

커밋 하나는 그 시점 전체 트리의 스냅샷 + 부모 커밋 포인터 + 메타데이터를 SHA-1 해시로 봉인한 불변 객체입니다. 브랜치는 그저 커밋을 가리키는 가벼운 포인터(파일 하나, 41바이트)이고, HEAD는 "지금 내가 서 있는 브랜치"를 가리키는 포인터입니다.

이 사실 하나로 많은 것이 설명됩니다: 브랜치 생성이 즉시 끝나는 이유, merge가 "포인터 이동 또는 부모가 둘인 커밋 생성"인 이유, rebase가 "커밋을 복사해 새로 만드는 것"이라 해시가 바뀌는 이유.

주의: git add . 습관은 비밀키·빌드 산출물을 커밋하는 사고로 이어집니다. .gitignore를 먼저 정비하고, git status로 확인 후 add 하세요.

브랜치 시뮬레이터 — merge vs rebase를 눈으로

아래 터미널에 명령어를 직접 입력하세요. 버튼은 입력 보조일 뿐입니다. 특히 같은 상황에서 merge와 rebase가 어떻게 다른 그래프를 만드는지 비교해 보세요. git reset --all로 언제든 초기화할 수 있습니다.

테두리 굵은 점 = 현재 위치(HEAD) main 두 번째 브랜치◎ 안이 흰 점 = 병합(merge) 커밋점 위에 마우스를 올리면 메시지가 보입니다

🧪 실습 과제 A — 3-way merge 만들기

git commit -m "A"
git checkout -b feature/search
git commit -m "B"
git commit -m "C"
git checkout main
git commit -m "D"        # main도 앞으로 나아감 → 갈라짐
git merge feature/search  # 부모가 둘인 merge 커밋 생성

D 없이 바로 merge하면 fast-forward(포인터만 이동)가 됩니다. 두 경우를 모두 해 보세요. --no-ff는 ff 가능해도 항상 merge 커밋을 남기는 옵션입니다.

🧪 실습 과제 B — rebase로 일직선 만들기

git reset --all
git commit -m "A"
git checkout -b feature/search
git commit -m "B"
git checkout main
git commit -m "D"
git checkout feature/search
git rebase main          # B가 D 뒤로 '복사'됨 (해시 변경!)
git checkout main
git merge feature/search  # 이제 fast-forward

rebase 후 B의 해시가 달라진 것을 git log로 확인하세요. 이것이 "이미 push한 공유 브랜치는 rebase하지 않는다"는 황금률의 이유입니다.

🔀 merge

장점 이력이 사실 그대로 보존, 안전(비파괴). 공유 브랜치에 사용.
단점 merge 커밋이 많아지면 그래프가 복잡.
팀 관례 feature → main 통합은 PR의 Merge/Squash로.

📐 rebase

장점 일직선의 깔끔한 이력, bisect·리뷰가 쉬움.
단점 커밋을 다시 쓰므로 해시 변경 → 공유 브랜치엔 금지.
팀 관례 내 로컬 feature를 최신 main 위로 올릴 때(git pull --rebase), 또는 rebase -i로 커밋 정리.

3

브랜치 전략 — GitHub Flow · Git Flow · Trunk-Based

브랜치 전략은 "브랜치를 언제 만들고, 어디서 뽑고, 어디로 합치고, 언제 배포하는가"에 대한 팀의 합의입니다. 입사한 팀의 CONTRIBUTING.md나 PR 템플릿에 보통 명시되어 있으니 가장 먼저 확인하세요. 각 탭의 ▶로 흐름을 재생하며 그래프 모양을 기억해 두면 좋습니다.

규칙① main은 항상 배포 가능 ② 모든 작업은 main에서 뽑은 설명적 이름의 브랜치 ③ 수시로 push ④ PR로 리뷰 ⑤ 승인 후 merge → 즉시 배포
적합SaaS·웹 서비스, CI/CD가 있는 소~중규모 팀. 대부분의 스타트업 기본값.
주의main에 바로 push 금지(Branch protection). 브랜치는 며칠 안에 닫히도록 작게. 배포 전 스테이징 환경이 없다면 Release Flow 변형을 고려.
브랜치 역할main 출시본·태그 / develop 통합 / feature/* develop에서 분기 / release/* QA·버전 준비 / hotfix/* main에서 분기, 양쪽 merge
적합모바일 앱·온프레미스 패키지처럼 버전 단위로 묶어 배포하고, 여러 버전을 동시에 유지보수해야 하는 팀.
주의브랜치 수명이 길어 merge 지옥·충돌이 잦음. 제안자(Vincent Driessen) 본인도 2020년 "지속 배포 웹앱에는 GitHub Flow가 낫다"고 덧붙였습니다. git-flow CLI 확장이 존재.
규칙모두가 trunk(main)에 하루 1회 이상 통합. 브랜치를 써도 수명 1~2일 이내. 미완성 기능은 Feature Flag로 숨김. 릴리스는 trunk에서 태그 또는 짧은 release 브랜치.
적합테스트 자동화와 코드 리뷰 문화가 성숙한 팀, 하루 수십 번 배포하는 대형 서비스(Google·Meta 등).
전제 조건빠른 CI(10분 내), 높은 테스트 커버리지, 작은 PR, 페어/몹 프로그래밍 또는 즉시 리뷰. 이게 없으면 trunk가 자주 깨집니다.

팀 협업 워크플로 — clone부터 PR merge까지

실무에서 하루에도 몇 번씩 반복하는 루프입니다: 최신 main → 브랜치 → 커밋 → push → PR → 리뷰 → merge → pull. 왼쪽은 내 로컬, 오른쪽은 origin(GitHub)입니다. 각 단계에서 두 저장소의 포인터가 어떻게 달라지고 다시 맞춰지는지 관찰하세요.

💻 Local (내 PC) 나나 (author)

☁️ origin (GitHub) 민민수지지은

Openfeature/login: 로그인 화면 추가 #42
나 wants to merge 2 commits into main from feature/login

📝 좋은 PR의 조건

· 작게: 리뷰 가능한 크기(±300줄 이내 권장)
· 한 가지 목적: 리팩터링과 기능 추가를 섞지 않기
· 설명: 무엇을·왜·어떻게 테스트했는지, 스크린샷, 이슈 번호(Closes #42)
· 셀프 리뷰: 올리기 전 diff를 스스로 한 번 읽기
· CI 초록불 확인 후 리뷰어 지정

👀 리뷰 받기·하기

받을 때: 방어하지 말고 질문으로 이해하기. 반영은 같은 브랜치에 커밋 후 push(자동 갱신). 논의가 길어지면 통화.
할 때: 의도 → 설계 → 세부 순으로. "nit:" 접두어로 사소한 것 구분. 칭찬도 코멘트로. 48시간 내 응답이 예의.

🔀 Merge 방식 3가지

Merge commit: 이력 보존, 그래프 복잡.
Squash and merge: PR 전체를 커밋 1개로. main이 깔끔(스타트업 기본값).
Rebase and merge: 커밋을 main 위에 일직선 재배치.
팀 설정을 따르되, Squash 뒤엔 로컬 feature 브랜치를 반드시 삭제하세요(해시가 달라 재사용 불가).

🔄 main이 먼저 바뀌었을 때 (PR 중 동기화)

git fetch origin                 # 원격 상태만 받아오기 (작업 트리 변경 없음)
git rebase origin/main           # 내 커밋들을 최신 main 위로 재배치 (충돌 시 해결 → git rebase --continue)
git push --force-with-lease      # 내 feature 브랜치만 안전하게 덮어쓰기 (--force 금지!)

또는 팀이 rebase를 꺼리면 git merge origin/main 후 일반 push. --force-with-lease는 그 사이 누군가 같은 브랜치에 push했다면 거부해 줍니다. Fork 기반(오픈소스)이라면 upstream 리모트를 추가해 같은 방식으로 동기화합니다.

충돌(Conflict) 해결 — 절차와 도구

충돌은 merge/rebase/cherry-pick/stash pop 어디서든 납니다. 원리는 하나: 같은 파일의 겹치는 영역이 양쪽에서 다르게 바뀌면 Git은 자동 병합을 포기하고 마커를 남긴 채 멈춥니다. 아래에서 merge 충돌을 직접 해결해 보고, 이어지는 명령 절차를 익히세요.

📄 price.md

🧭 해결 절차 (merge 기준)

git merge feature/promo
# CONFLICT (content): Merge conflict in price.md
git status                      # Unmerged paths 확인
# 에디터/IDE에서 <<<<<<< ======= >>>>>>> 블록 편집
git add price.md                # "해결했다"는 표시
git commit                      # merge 커밋 생성 (메시지 자동)
# 포기하려면: git merge --abort

rebase 중이라면 git add 후 git rebase --continue (commit 대신), 포기는 git rebase --abort. cherry-pick도 동일 패턴.

🛠️ 유용한 옵션·도구

· git checkout --ours <f> / --theirs <f> : 파일 단위로 한쪽 전체 채택 (rebase 중엔 ours/theirs 의미가 뒤집힘에 주의)
· git diff --name-only --diff-filter=U : 충돌 파일 목록
· git mergetool : 3-way 비교 툴 실행 (VS Code "Resolve in Merge Editor" 추천)
· git log --merge -p <f> : 충돌에 관여한 양쪽 커밋만 보기
· git rerere : 같은 충돌 해결을 기억해 재적용

예방이 최선: 작은 PR, 하루 1회 이상 fetch + rebase, 포매터(Prettier/Black) 통일로 "공백 충돌" 제거, 대규모 리네임은 사전 공지.
