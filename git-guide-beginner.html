Git, 그림으로 이해하기

Git은 "파일의 모든 변경 기록을 남기고, 여러 사람이 같은 자료를 안전하게 함께 고칠 수 있게 해주는 도구"입니다. 프로그래밍을 몰라도 괜찮습니다. 아래 버튼들을 직접 눌러보면서 저장·갈라짐·합치기가 어떻게 움직이는지 눈으로 확인해 보세요.

저장은 어떻게 이루어질까? — 4개의 방

Git을 처음 배울 때 가장 헷갈리는 부분은 "저장"이 한 번에 끝나지 않는다는 점입니다. 문서를 고친 뒤 상자에 담고 → 도장을 찍어 보관하고 → 공유 서버에 올리는 세 단계를 거칩니다. 버튼을 눌러 파일이 어느 방으로 옮겨가는지 보세요.

📁 내 책상 (작업 폴더)지금 고치고 있는 파일들

🧺 포장 상자 (스테이지)"이번에 기록할 것"만 골라 담는 곳

📚 내 서류함 (로컬 저장소)도장 찍힌 기록(커밋)이 쌓이는 곳

☁️ 공유 캐비닛 (원격 저장소)GitHub 등, 팀 모두가 보는 곳

🧺
add = 상자에 담기고친 파일이 여러 개여도, 이번 기록에 넣을 것만 골라 담을 수 있습니다. "선택적 저장"이 Git의 첫 번째 특징입니다.
📌
commit = 도장 찍기상자에 담긴 내용에 "누가, 언제, 왜 고쳤는지" 메모를 붙여 봉인합니다. 이 봉인 하나하나를 커밋이라 부르고, 언제든 그 시점으로 되돌아갈 수 있습니다.
☁️
push / pull = 올리기 / 내려받기도장 찍은 기록은 아직 내 컴퓨터에만 있습니다. push로 공유 캐비닛에 올려야 동료가 보고, 동료 것은 pull로 가져옵니다.
왜 이렇게 복잡하게? 워드의 "저장"은 이전 내용을 덮어쓰지만, Git의 커밋은 이전 기록을 절대 지우지 않고 쌓아 둡니다. 그래서 "지난주 화요일 버전으로 돌려줘"가 가능하고, 누가 어떤 줄을 바꿨는지도 전부 추적됩니다.
2

브랜치 — 원본을 건드리지 않고 다른 길로 가보기

브랜치(branch)는 "지금까지의 기록을 그대로 복사해 둔 평행 세계"입니다. 새 기능을 시도하다 망쳐도 원래 줄기(main)는 멀쩡합니다. 잘 되면 다시 합치면(merge) 됩니다. 버튼을 눌러 점과 선이 어떻게 갈라지고 합쳐지는지 보세요.

테두리 굵은 점 = 현재 위치(내가 서 있는 곳) main 두 번째 브랜치◎ 안이 흰 점 = 병합(merge) 커밋점 위에 마우스를 올리면 메시지가 보입니다

🌱 추천 순서로 눌러 보세요

  1. 기록 남기기를 두 번 → main 줄기에 점이 늘어납니다.
  2. 새 길 만들기 → 초록색 새 줄기가 생기고 내 위치가 그리로 옮겨갑니다.
  3. 기록 남기기를 두 번 → 새 줄기에만 점이 쌓입니다. main은 그대로!
  4. main으로 돌아가기 → 기록 남기기 한 번 → 두 줄기가 서로 다르게 자랐습니다.
  5. 합치기(merge) → 두 줄기가 하나의 "병합 점"에서 만납니다.

💡 비유로 이해하기

main = 회사에 제출하는 "최종 보고서". 항상 깨끗해야 합니다.

브랜치 = 보고서를 복사해 둔 "초안 v2". 마음껏 실험합니다.

merge = 초안에서 잘 된 부분을 최종본에 반영하는 것. Git은 두 쪽의 변경을 자동으로 맞춰 줍니다.

아래 검은 창은 "가상 터미널"입니다. 개발자들은 이 명령어를 직접 입력하지만, 비개발자는 버튼만으로 충분합니다. 궁금하면 help를 입력해 보세요.

3

팀은 브랜치를 어떻게 나눌까? — 3가지 협업 규칙

브랜치를 "언제 만들고 언제 합칠지"에 대한 팀의 약속을 브랜치 전략이라고 합니다. 정답은 하나가 아니고, 팀 규모와 배포 주기에 따라 고릅니다. ▶ 버튼으로 각 방식의 흐름을 재생해 보세요.

한 줄 요약main 하나 + 작업마다 짧은 브랜치. 작업이 끝나면 동료 검토(PR)를 받고 합칩니다.
이런 팀에 맞아요소규모 팀, 웹 서비스처럼 자주 배포하는 곳. 처음 배운다면 이것부터.
비유공유 문서 하나를 두고, 고칠 부분만 복사본에서 작업한 뒤 "검토 요청"을 보내 반영하는 방식.
한 줄 요약역할별로 브랜치가 5종류(main·develop·feature·release·hotfix). 체계적이지만 복잡합니다.
이런 팀에 맞아요앱·패키지 소프트웨어처럼 "버전 1.0, 2.0"으로 묶어 배포하는 대규모 팀.
비유출판사. 집필(feature) → 편집부 취합(develop) → 교정본(release) → 출간(main). 긴급 정오표는 hotfix.
한 줄 요약모두가 main(trunk, 줄기)에 거의 직접, 아주 작은 단위로 자주 합칩니다. 브랜치 수명은 하루 이하.
이런 팀에 맞아요자동 테스트가 잘 갖춰진 숙련된 팀, 하루에도 여러 번 배포하는 대형 서비스.
비유한 장의 화이트보드에 모두가 조금씩 바로바로 적어 넣는 방식. 미완성 기능은 "스위치(플래그)"로 꺼 둡니다.

4

여럿이 함께 일하기 — Pull Request(검토 요청)

팀 작업의 핵심은 "내 작업을 바로 공용 줄기에 넣지 않고, 동료에게 먼저 검토를 요청하는 것"입니다. 이 요청을 Pull Request(PR)라고 합니다. 왼쪽은 내 컴퓨터, 오른쪽은 GitHub(공유 캐비닛)입니다. 두 곳이 어떻게 맞춰지는지 따라가 보세요.

💻 내 컴퓨터 나나

☁️ GitHub (공유 캐비닛) 민민수지지은

Openfeature/login: 로그인 화면 추가 #42
나 wants to merge 2 commits into main from feature/login

🙋 PR은 왜 필요할까?

혼자 고쳐서 바로 올리면 실수가 그대로 모두에게 퍼집니다. PR은 "이렇게 바꾸려는데 봐 주세요"라는 결재 요청과 같습니다. 두 번째 눈이 오류를 잡고, 팀원 모두가 변경 이유를 기록으로 남길 수 있습니다.

👀 리뷰에서 하는 일

Approve(승인) – 이대로 합쳐도 좋다.
Request changes(수정 요청) – 이 부분을 고친 뒤 다시 보자.
Comment – 의견만 남김.
수정 요청을 받으면 같은 브랜치에 고쳐서 다시 올리면(push) PR에 자동으로 반영됩니다.

🔁 pull을 잊지 마세요

PR이 GitHub에서 합쳐져도 내 컴퓨터의 main은 아직 예전 상태입니다. 마지막에 git pull로 최신 상태를 내려받아야 다음 작업을 최신본 위에서 시작할 수 있습니다.

두 사람이 같은 줄을 고쳤다면? — 충돌(Conflict)

Git은 대부분 알아서 합쳐 주지만, 같은 파일의 같은 줄을 두 사람이 다르게 고치면 어느 쪽이 맞는지 판단하지 못하고 사람에게 묻습니다. 이것이 "충돌"입니다. 무섭게 들리지만, 실제로는 "둘 중 어떤 문장으로 할까요?"라고 물어보는 것뿐입니다.

📄 price.md

충돌은 사고가 아닙니다. Git이 "여기 두 의견이 다르니 결정해 주세요"라고 안전하게 멈춘 상태입니다. 당황하지 말고 ① 표시된 두 구간을 읽고 ② 최종 문장을 정한 뒤 ③ 표시 기호를 지우고 ④ 다시 도장(commit)을 찍으면 끝입니다.

🔖 기호 읽는 법

<<<<<<< HEAD 부터 ======= 까지 = 내 쪽 내용
======= 부터 >>>>>>> 까지 = 상대 쪽 내용
세 줄의 기호는 Git이 임시로 넣은 표시이므로 반드시 지워야 합니다.

🛡️ 충돌을 줄이는 습관

· 작업 시작 전에 항상 git pull로 최신본 받기
· 브랜치를 오래 끌지 않고 작은 단위로 자주 합치기
· 같은 파일을 동시에 고칠 일이 있으면 미리 한마디 하기

6

정리 — 꼭 기억할 말들과 퀴즈

명령어를 외울 필요는 없습니다. 개발자와 대화할 때, 혹은 GitHub 화면을 볼 때 아래 단어들이 무엇을 뜻하는지만 알면 충분합니다.

📦 저장 흐름

add이번에 기록할 파일을 상자에 담기
commit메모를 붙여 도장 찍기(기록 1개 생성)
push내 기록을 공유 서버에 올리기
pull서버의 최신 기록을 내려받기
clone서버의 프로젝트를 통째로 내 컴퓨터에 복사

🌿 브랜치

branch평행 세계(갈래) 하나
main항상 깨끗해야 하는 기본 줄기
checkout / switch다른 갈래로 자리 옮기기
merge두 갈래를 하나로 합치기
conflict같은 줄을 다르게 고쳐 Git이 결정을 요청한 상태

🤝 협업 (GitHub)

Pull Request"내 갈래를 합쳐 주세요" 검토 요청
Review / Approve동료가 내용을 보고 승인
MergePR을 승인 후 실제로 합치기
Issue할 일·버그를 적어 두는 게시판
Fork남의 프로젝트를 내 계정으로 통째 복사
